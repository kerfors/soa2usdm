SoA2USDM - from the printed table to schemas

A Schedule of Activities table is a 2D presentation of study logic, constrained by paper. Footnotes are the overflow for logic that does not fit the grid. SoA2USDM transcribes the table into five constructs, carries them through three schemas, and lets human judgement in only through sidecars. Stating the result in USDM is a separate step that is still being explored.

How corrections work

Review finds things. A reviewer does not edit a file; the reviewer writes an entry in a sidecar, and a program applies it. There are two sidecars, one before Layer 2 and one before Layer 3.

The human is an adjudicator, not an editor. Judgement enters through an auditable sidecar, never by rewriting model output.

The idea of a study shell

  • USDM has no standalone serialization of an SoA. A ScheduleTimeline hangs under a StudyDesign, under a StudyVersion, under a Study.
  • A StudyDesign mandates arms, cells, elements, a population, eligibility criteria and a model. An SoA contains none of these.
  • The shell is that surrounding structure, built from a manifest of a few facts about the protocol: identifier, title, sponsor, epoch list (usdm-manifest v1.0). What is not stated is emitted as an object flagged not stated.
  • The shell and the SoA meet at exactly one attribute, ScheduledInstance.epochId. The epoch list is the one part of the shell the SoA really needs.

The SoA lifting

  • The consolidated table is rendered as USDM schedule objects: activities and scheduled instances in a timeline and, where the table supports it, timings and encounters.
  • Which column property carries the epoch axis is an interpretation. It is stated outside the Layer 1-3 schemas and logged as a decision.
  • Each build is checked against a pinned usdm-rdf release.

What a full-fledged instantiation would need. SoA patterns, to interpret what the timeline and the notes express, and potentially some kind of shared nomenclature. Neither is part of soa2usdm today.
