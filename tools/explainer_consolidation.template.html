SoA2USDM - consolidation of tables

Consolidation is the point where the pipeline stops working per table. The resolved tables of one protocol become one schedule: rows that print the same activity are matched, the columns of each table are placed on timeline segments, and a note printed in several tables is kept once. It is done by program. Whether two rows are the same activity stays a human statement, made in a sidecar.

What consolidation does

  • matches activity rows across tables
  • places every column on a timeline segment, by table type
  • keeps a note printed in several tables once, with every occurrence
  • rebuilds the schedule matrix on the cross-table ids
  • applies the human match decisions, and counts what is left to decide
  • carries every table's extraction review items, tagged with the table

What it leaves

  • columns are not matched across tables
  • no reading of what the timeline or the notes mean: epochs, timings, conditions
  • no USDM objects. That is USDM Instantiation, a separate step

The table type decides the route

The extraction classifies every table (table_metadata.table_type). Consolidation reads that type and nothing else to decide whether the table's rows are matched and on which segment its columns go. Tables are processed in a fixed order.

1. The base
the lowest-numbered main_soa. Its rows become the first activities, xact-001 onwards.
→
2. Further main_soa tables
by table number, matched against what exists.
→
3. All other tables
by table number, matched; reference tables skipped.
{{TYPE_CARDS}}

Order matters twice. A row can only be matched to an activity made from a table processed earlier, so the pair has a direction: the source is the later row, the target the earlier one. And xact ids are counters in this order, so they change when the input changes. That is why the match decisions sidecar names rows, never xact ids. In the published collections: {{N_PROTOCOLS}} protocols, {{N_TABLES}} tables; {{N_SINGLE}} protocols have a single table, so consolidation only re-addresses them.

3

Three axes, three strategies

An SoA table has two axes and its notes. Consolidation treats each differently: rows are matched, columns are placed side by side, notes are deduplicated on their text. The schedule matrix is then rebuilt on the new ids. Hover a part of the drawing or a card.

Schematic. Letters stand for activity rows, numbers for visits, X for a schedule mark, n for a note.
Rows
matched
Activities → unified_activities[]

A row of a later table joins an activity that already exists, or starts a new one (part 4). An activity takes at most one row per table. Every row it holds stays listed in source_refs, with how it came there: match_status, match_confidence and, when a human decided, decision.

Columns
placed
Columns → timeline_segments.<segment>[]

Not matched. Every data column of every table becomes its own xcol, on the segment its table type gives it. Columns of different tables line up only through property_hierarchy: header rows with a level unify by level, rows without one (window, modality, visit attribute) by type and name. Even a domain table, printed on the main timeline, keeps its own columns ({{DOM_PID}}: {{DOM_MAIN}} main + {{DOM_DOMAIN}} domain).

Notes
deduplicated
Annotations → unified_annotations[]

A note whose text is identical, after lower case and collapsed spaces, to a note already seen is the same note. It is kept once, with every source_occurrences entry (table, marker, annotation id). What each occurrence binds to is re-pointed to xact, xcol and unified property ids.

Cells
re-addressed
Schedule marks → schedule_matrix[]

One cell per xact_id × xcol_id, with source_values keyed by table. Since a column belongs to one table, a cell holds the value of exactly one table; true for all {{N_CELLS}} cells in the published collections.

4

Matching rows

Each row of a table after the base is compared with the activities made so far. Four steps, in order; the first that finds a candidate decides. Only activities that hold no row of the same table yet are candidates, and among several the best score wins.

1
Same parent, same name

The qualified key parent::name is one already made. Names compared as printed, case included.

exact merged, score 1.0. Not listed for review.
2
Same name, any parent

The name equals the name of an activity, whatever its parent.

exact merged, score 1.0. Not listed for review.
3
Similar name, same parent

The best name score among activities under the same parent row.

fuzzy_auto score ≥ {{AUTO}}: merged, and listed for review
near match {{REVIEW}} ≤ score < {{AUTO}}: not merged. The row becomes an activity of its own and carries the candidate as a hint, near_matches, listed for review
4
Similar name, other parent

The best name score among activities under another parent; section headers are not candidates.

fuzzy_cross_parent score ≥ {{CROSS}}: merged, listed for review; the activity's parent_name becomes “A / B”
–
Nothing found

No step found a candidate.

new a new activity
✎
Then the human decision

If the sidecar has an entry for this row, it is applied to what the steps found (part 5).

keep / split / merge recorded as decision on the row or on the hint
  1. Lower case; hyphen and slash read as a space; text in parentheses removed.
  2. Split on spaces; other punctuation stays on the word (‘medical,’). Words of one or two characters dropped; a plural ‘s’ dropped (not after ss, us, is).
  3. Compare the two word sets.

Coverage lets a short name inside a longer one score high; the Jaccard part pulls the score down when the longer name adds much. Below {{AUTO}} a merge is an identity judgement, not a wording variant, so the program does not make it: it leaves a hint for a human.

coverage = shared / size of the smaller set
jaccard  = shared / size of the union
score    = 0.6 × coverage + 0.4 × jaccard

Match decisions: the Layer 3 sidecar

Every match a name score made or nearly made is listed for review: each row merged on a similar name, each row merged or split by a decision, and each near match. A match is decided exactly when an entry of the sidecar names it. Rows merged on an identical name are not listed. Schema: {{CCORR_SCHEMA}}, file consolidated/<protocol>_consolidation_corrections.json.

That two rows are the same activity is a human statement, not a pipeline result. The sidecar is read before matching, and an entry whose premise no longer holds stops consolidation.

An entry, as written

From {{OP_JSON_FILE}}. Rows are named by table number and activity id; the activity name is carried as a check.
{{OP_JSON}}

Every entry is checked

  • both rows exist, under the name the entry states
  • neither is in a reference table, and the two are in different tables
  • keep, split, merge: at most one per source row; the target's table is consolidated before the source's table, so a row of the base table cannot be a source; the premise of the op holds
  • no draft placeholder is left in reason or by

The names are checked against the resolved tables before matching, the premises while matching. Any failure stops consolidation with the entry id: a decision is never silently dropped when the extraction or the matching changes underneath it.

The review in the published collections

Rule applied: the same row only where the names differ in spelling, hyphen, case, word order or abbreviation, or a footnote states the difference. Rows that name different content or another population stay separate.

7

The consolidated view

Each protocol's consolidated file is rendered as one page. The matches are reviewed there, against the schedule they shape. The page writes nothing: a choice drafts a sidecar entry, and the sidecar stays the only write path.

One grid per segmentThe main schedule first, then each track, domain or subsidiary segment; the header rows from property_hierarchy, and an In column saying which tables print the row.
Matches across tablesEvery match listed for review: its state, the two rows with the words that differ marked, what consolidation did and at what score, and the decision.
A decision drafts an entryChoosing keep, split or merge writes the JSON to append to the sidecar. Consolidation is re-run; the page then shows the match as decided.
